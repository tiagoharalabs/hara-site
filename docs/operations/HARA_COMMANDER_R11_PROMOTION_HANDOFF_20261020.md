# HARA Commander — R11: handoff de distribuição e promoção

Estado em 20/10/2026: **HOLD para instalação comercial pública**. O GET independente do endpoint principal retornou manifesto 0.3.41, assinatura v1 incompatível com o pin v2 do instalador Linux servido e quatro assets fora dos hashes assinados. Exit 2 do gate ao vivo é falha real, não PASS. O 401 isolado do Observer não foi reproduzido e permanece outra investigação.

## Candidato e prova local

`build_commander_commercial_terminal_drain_candidate.py` prepara uma fonte 0.3.43 sem assinatura: Linux com drenagem pós-exit e instaladores que validam o pacote antes do cadastro; Windows Agent comercial permanece 0.3.43. A fonte funcional Windows 0.3.55 da R10 está separada. Não tratar o candidato 0.3.43 como prova de paridade Windows nem publicar sem uma assinatura oficial sobre seus bytes finais.

`stage_signed_commercial_assets.py` exige o bundle corrente `commercial-0.3.43-v5-terminal-drain`, ainda ausente. O novo `require_signed_stage` confere assinatura RS256 com pin v2, manifesto, hashes/tamanhos, os oito arquivos de release byte a byte contra o bundle aprovado, todos os outros arquivos rastreados contra o `public/` atual e as regressões Linux, inclusive a saída pós-exit. O bundle v4 assinado só passa no modo histórico de rollback e falha no teste funcional de terminal.

`commander_versioned_prod_promote.py` agora exige `--stage` absoluto. Faz essa validação **antes** de consultar Wrangler; com `--execute`, promove uma versão única a 100% e depois exige readback de versão, assets exatos do staging e integridade pública independente. Não aceita `public/` bruto como staging. Um timeout ou readback falho após o comando mutante deixa o estado **incerto**: ler o deployment atual antes de decidir rollback ou nova ação; não repetir a promoção às cegas.

## Sequência pendente de autorização

1. O responsável pela assinatura deve decidir a composição final Linux/Windows e assinar oficialmente o manifesto com a chave v2 sob custódia, sem exportar a chave. Validar o bundle completo e a correção pós-exit; nenhum hash isolado equivale a assinatura ou teste funcional.
2. Gerar um staging novo com o script acima e guardar do relatório `stage_tree_sha256` e `source_public_tree`. O primeiro vincula **todos os 17 arquivos rastreados** do estágio (oito de release e nove de UI/configuração estática); o segundo identifica a árvore Git pública revisada. Para este v5 congelado, a árvore deve ser `2138ef35e0f9bee92888e1bcf7bb5212956170bd` (fonte `a13b4d2`); outra UI exige novo candidato e revisão. Só os oito arquivos de release têm assinatura criptográfica: o digest da UI não a transforma em conteúdo assinado. Verificar o mesmo diretório com `stage_signed_commercial_assets.py --verify-assets <stage> --expected-tree-sha256 <digest>`. O upload autorizado deve passar por `commander_versioned_prod_upload.py --stage <stage> --stage-tree-sha256 <digest> --source-public-tree <tree> --message <motivo> --execute`. Esse wrapper copia os assets para snapshot privado, verifica seu digest, passa **o snapshot** ao `wrangler versions upload --assets` e depois revalida snapshot e origem. Sem `--execute`, faz apenas preflight local. Retorno `UPLOAD_SUBMITTED_VERSION_READBACK_REQUIRED` ainda tem `version_content_verified=false`: exige identificar versão e conferir seus assets antes de promover tráfego; snapshot não substitui readback Cloudflare. Timeout/erro de upload é estado **desconhecido**, exige leitura remota da versão e não autoriza retry cego. Uma versão do Worker contém código e assets estáticos como unidade, segundo a [documentação da Cloudflare](https://developers.cloudflare.com/workers/versions-and-deployments/). Não usar `wrangler deploy` direto nem upload de arquivos soltos.
3. Ler a versão carregada, bindings e nomes de secrets, e qualificar uma versão de rollback que preserve a distribuição e as funções atuais. A v4 histórica possui regressão de drenagem; não é fallback funcional automático. Migrações D1 não voltam com rollback de Worker. **O upload, sozinho, não prova seus bytes remotos.** Este Worker tem `preview_urls: false` e Durable Objects; [Cloudflare não gera Version URLs para Workers com Durable Objects](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/). A alternativa documentada é um deployment explicitamente autorizado de **rollback 100% + candidato 0%**, seguido de [GETs com version override](https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/). Mesmo 0% é mutação de PROD e requer autorização específica; requisições públicas com o version ID podem alcançar o candidato, portanto 0% não fornece isolamento de acesso. Nenhuma foi executada nesta frente.
4. Após esse deployment 0% autorizado, executar `python3 -B apps/commander/scripts/commander_versioned_asset_readback.py --stage <stage> --stage-tree-sha256 <digest> --version <candidate-id> --rollback <current-id>` de ambiente coordenado. O gate exige estado 0%/100% antes e depois, compara por HTTPS os **15 assets públicos** da versão com o stage e exige que ao menos um asset do deployment atual seja diferente; o HTML da raiz permite somente a normalização de beacon já usada no readback público. Se o override for ignorado, indistinguível ou falhar, retorna HOLD. O resultado `VERSION_ASSETS_VERIFIED_0_PERCENT` prova somente os assets HTTP naquele readback, vinculados ao version ID no deployment; não atesta os bytes do código Worker nem todos os POPs. A leitura da versão, bindings e secrets continua separada. Não usar 0% nem o readback para contornar a assinatura ausente.
5. Somente com aprovação específica, executar a promoção versionada com `--stage`, `--stage-tree-sha256`, `--version`, `--rollback` e `--execute`. O promotor repete o gate acima **antes** de `wrangler versions deploy` 100%. Depois, verificar o deployment 100%, os 15 assets HTTP públicos byte-idênticos ao staging (incluindo HTML, JS, CSS, marcas e pin v2), assinatura sob o pin dos instaladores realmente servidos e 4/4 hashes. Os dois arquivos de controle `.assetsignore` e `_headers` ficam no digest do estágio, sem GET público. Repetir o gate GET a partir de Services, Storage e Observer para observar POPs distintos. Um PASS em um host não prova todos os POPs.
6. Após o readback assinado, realizar clean install comercial isolada em Fedora 43/SELinux e Ubuntu 22/UID 1001, depois Windows 11, com rollback e sem afetar os Agents Founder. O canário Founder Sentinela A 0.3.54 da R12 já foi feito por outra frente autorizada; não é validação da instalação comercial pública.

## Critério mínimo de latência para o canário comercial

Para o aceite da jornada `read_file`/leitura paginada, separar `EVENT_V2` Linux e `OUTBOUND_RELAY` Windows, e reportar por dispositivo, transporte e ferramenta. A proposta de gate é **p95 total ≤ 6.000 ms** (limite já existente no perfil `INTERNAL_BETA_V1`) e **p95 de fila ≤ 3.000 ms** (orçamento novo para distinguir espera de execução), com pelo menos **100 chamadas concluídas por grupo** em QA/DEV ou canário especificamente autorizado, distribuídas por mais de uma janela. Medir p50/p99 e falhas de serviço separadas de negativas de cliente/política. Qualquer grupo ausente ou abaixo de 100 é `INSUFFICIENT_DATA`, nunca PASS por média da frota. Esta proposta é critério de promoção, não SLA já homologado. A amostra R16c de quatro chamadas por host, embora 12/12 PASS, não atende à cobertura e não identifica causa. O `get_activity` atual limita o histórico recente a 100 chamadas **no total**, portanto exige coleta filtrada e sanitizada para preencher esses grupos; não extrapolar seu p95 para a janela de 24h nem gerar carga em PROD sem autorização.

O fluxo atual usa um único deploy versionado do Worker; ainda **não** implementa URLs imutáveis por release com ponteiro público atualizado por último. A validação pré-enrollment falha fechada se requisições públicas cruzarem bytes de releases diferentes. Readback multiponto e eventual desenho de ponteiro imutável continuam necessários antes de declarar entrega pública estável. Nada neste handoff autoriza assinatura, upload, promoção, migração remota, instalação ou cutover.
